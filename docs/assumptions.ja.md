# ScanMux の結果が前提にしていること

ScanMuxの結果を判断に使う前に、ツール自身では確かめられない前提と、結果が保証しないことを確認してください。

この日本語版が正本です。英語版はこの文書の翻訳です。

各記述は、末尾の変更履歴にある日付時点のコードを説明しています。

## v0.2.1 の範囲

対応する言語の入力、緊急脆弱性の照合、対象外の範囲は、[READMEの「v0.2.1 の範囲」](../README.ja.md#v021-の範囲)を参照してください。対応とは利用できる検査を指し、完了の保証ではありません。以下の結果の意味と信頼の前提は引き続き適用します。

## 結果の意味

ScanMux の結果は5種類です。

`PASS`（終了コード 0）は必須エンジンがすべて完了して全範囲を解析し、対応や確認の要る検出が1つもないとき、`FAIL`（1）は秘密情報か、ソースで裏付けられたか実行時に再現した High/Critical の検出があるとき、`REVIEW`（2）は High/Critical の候補か深刻度不明の検出があるとき、`INCOMPLETE`（3）は必須の検査が欠けた・除外された・止められた・非対応・部分的・中断・時間超過のときです。

5つ目の `ERROR`（4）は実行の失敗か完全性の誤りで、ほかの4つより優先され、そのあとは `FAIL`、`INCOMPLETE`、`REVIEW`、`PASS` の順です。
現時点では、どのコマンドも `PASS` を出せません。
すべての計画が `runtime-advisories` エンジンを必須にしていて、このエンジンは常に部分的か非対応の範囲を報告するので、通常の `scan` でも `ai-scan` でも必須の検査が完了しないからです。

通常の `scan` では、必須の AI エンジンも動きません。

## 任意の論理コピー容量上限

設定（schema 1/2）とオフラインジョブプロファイル（v1/v2）の最上位に置く任意の`maxCopyBytes`は、バイト単位の正の安全な整数です。
`host-job-scan`が参照するオフラインプロファイルでも指定できます。
リポジトリごとに決め、既定値はありません。

ScanMux自身が作る来歴確認用の実行資材・bundle・trusted root、OSVのZIP、固定アプリ、Windowsプロセス所有者、Trivyのコピーの論理バイト数を制限します。
出力先の作成前にコピー元のサイズ分を予約し、途中で元が増えた場合も、各部分を書き込む前に上限を確認します。
検証済みサイズとの不一致やコピー中のサイズ変化は、呼出し元の完全性エラーとして扱います。

来歴確認用の実行資材・bundle・trusted rootには期待サイズを記録していないため、大きいファイルへの差替えで残予算を超えると、ハッシュ検査が変更を`ERROR`として報告する前に`job_disk_copy_limit`（`INCOMPLETE`）となります。
成功分は予算を使い、拒否・失敗分は途中出力を削除するまで予約を保持します。
削除失敗は予約を保持したまま入出力エラーにします。

単独ジョブではホスト側の残予算を一時的な起動メッセージでLinux管理役へ渡します。
保存結果のschemaや保存記録の容量計上は変えず、キーの省略時は既存の動作と形式を維持します。

単一スキャンのコマンド（`scan`・`ai-scan`・`resume`）では、受付時のコピー、プロセス所有者の実行ファイル、スキャン中のコピーで1つの予算を共有します。
`serve`・`scan-list`など複数のスキャンを実行するコマンドでは、各`scan()`が自身の設定から新しい予算を作ります。
コマンド側の受付とプロセス所有者のコピーには、コマンドの設定上限を使う別の予算を割り当てます。

スキャン側でキーを省略した場合、コマンド側の予算は引き継ぎません。

上限到達は`job_disk_copy_limit`を原因とする`INCOMPLETE`で、先行する`FAIL`・`ERROR`を優先します。
管理役の起動前の拒否では既存のエラー形式で終了3を返します。`deps`では、これらの失敗も終了2です。
Windowsの`host-job-scan`は、参照するオフラインプロファイルの最上位キーを使います。
親が受付コピーを計上し、残予算だけを一時的な管理役・workerの起動引数で渡します。

workerは自分の受付コピーとアプリコピーを差し引き、残りを既存の起動メッセージでLinuxへ渡し、前段へ予算を戻しません。
`D/app`の作成前にアプリ全体のmanifestが残予算に収まることを確認するため、予算不足で部分的なアプリは残しません。
サイズ・ハッシュ変化は完全性エラーのままです。
worker・Linuxでの不足は既存の報告理由に記録し、エラー・取消・期限の優先順位を維持します。

ホストv1/v2の保存形式・検証器・保存記録の容量計上は変えず、キー省略時は管理役の起動引数も維持します。

外部エンジンの書込み、スナップショット展開、報告・途中保存の生成、Docker/OSの保存領域、ファイルシステム管理情報、書出し先は対象外です。
論理バイト数は物理割当量とは異なります。
強制的な物理上限ではなく、物理quotaにはScanMuxが変更しないOS側の設定が必要です。
登録したジョブ領域は、後述の任意の計測上限で別に扱います。

試験は上限一致・超過・予約共有・コピー元の増加と中断・削除失敗・拒否の伝達・旧記録の維持を確認しますが、物理quotaの証明ではありません。

## ジョブディスク使用量の任意の計測上限

設定（schema 1/2）の最上位で`maxCopyBytes`の隣に、任意の`maxJobDiskBytes`を置けます。
バイト単位の正の安全な整数をリポジトリごとに指定し、既定値はありません。
`scan`・`ai-scan`・`resume`は、来歴確認・プロセス所有者・スキャンを一つの計測範囲で扱います。

`serve`・`scan-list`では各`scan()`が新しい計測範囲を持ち、そのスキャン領域と共用するプロセス所有者の実行ファイル領域を含めます。
`job-scan`でもジョブプロファイルの最上位に指定でき、`host-job-scan`では参照先のオフラインジョブプロファイルの値を使います。
ホストの`limits`や`retained`には項目を追加しません。
値は実行時の起動メッセージで渡し、保存するLinux Configには含めません。

省略時は既存の動作・管理役とworkerの引数・保存形式を維持します。

これらのジョブコマンドでは、登録したホスト側のジョブ領域（アプリのコピーと保存記録を含む）と、コンテナー内の`/work`・`/tmp`・`/dev/shm`を合算します。
ホスト側は、`job-scan`ではTypeScriptの親、`host-job-scan`ではWindows workerが計測します。

コンテナーの管理役も同じ走査処理を使い、既存のsupervisor通信で計測値を送り、ホスト側が最新のホスト計測値と合算してエンジンの停止を要求します。
両側の計測は同時刻ではありません。
読取り専用の`/app`は重複計上せず、計測によって保存容量のカウンターは増やしません。
既存のLinux tmpfs制限は別に適用します。
Dockerデーモン・イメージやVM・OSの保存領域、ファイルシステムのメタデータは対象外で、物理quotaは保証しません。

ScanMuxが作成時に登録する対象は、スキャン領域（snapshot、エンジンのTEMP・cache、準備したOSV ZIP、チェックポイントを含む）、プロセス所有者の領域、`W`・`bin`を含むTrivy領域、一時的な来歴確認領域です。
登録時に実体パスへ正規化し、入れ子や別名（Windowsでの大文字・小文字の違いを含む）による同じ領域の登録を重複計上せず、削除する一時領域は登録を解除します。

通常ファイルのサイズを、それぞれのファイルシステムのクラスタサイズ（`statfs().bsize`）単位で切り上げて合算します。
ディレクトリは0バイトとし、シンボリックリンクやジャンクションの参照先はたどりません。
v2の保存記録を含め、登録領域の外側は計上しません。

外部プロセスの実行中は100ミリ秒間隔で計測し、プロセスの終了確認後と各エンジンの終了時にも計測します。
推定量の上限を超えたら、既存のプロセスツリー終了確認の経路で解析を停止します。
`job_disk_measured_limit`は`INCOMPLETE`、終了を確認できなければ既存の`termination_unverified`による`ERROR`です。
走査中に消えたエントリは存在しないものとして扱い、置換されたエントリは読み直します。

親ディレクトリの再列挙で名前が見つからない場合（Windowsでは大文字・小文字を区別せず比較）、またはその後のstatで消失を確認できた場合に、存在しないものとして扱います。
再列挙でも名前が残り、読み取れない場合は`ERROR`のままです。
登録ルートの欠落、継続する権限・statのエラー、クラスタサイズを取得・確認できない場合は、0バイトとして扱わず、`job_disk_observation_unverified`で停止して`ERROR`にします。

利用者の中止やスキャン期限が先なら、終了時の計測で後から容量超過や観測エラーが生じても、最初の停止理由を維持します。
先に出た`FAIL`・`ERROR`の優先順位は維持します。
停止原因を保存するため、容量停止後も既存の上限がある出力の秘密検査と最終記録・レポートの書込みは行います。
この完了処理の書込み量は制限しません。

これは計測した推定量であり、物理割当量やファイルシステムのquotaではありません。
ScanMuxはOS設定を変更しません。
疎ファイル・圧縮ファイル・ハードリンクでは物理割当量と異なる場合があります。
計測間の増加や、計測前に作成・削除された短命なファイルは見逃すことがあります。
計測中に名前が変わったディレクトリは、次の計測まで見逃す場合もあります。

書込み速度に上限がある場合でも、計測間隔、走査・スケジューリングの遅延、終了確認にかかる時間の間の増加量に、一括書込みと各ファイルのクラスタ切上げ分を加えた超過余裕が必要です。
これらに上限がなければ、一律のバイト超過上限は保証できません。
ファイルシステムのメタデータ、代替データストリーム、Docker・OSの保存領域（AppContainerのプロファイル領域を含む）、共用する所有者ジャーナル、エクスポート先は推定量の対象外です。

したがって、物理的な強制上限は保証しません。

## 結果が信頼するツールと環境

各項目は4つの部分でできています。「検査」の欄にある検査は、前提が破れる一部の形を見つけます。検査は、前提が成り立つことの証明ではありません。

### 固定したツールの実行ファイルと版

**前提。** `tools.git`、`tools.gitleaks`、`tools.osv` に固定した実行ファイルは、その版の正規の配布物で、配布元の説明どおりに動きます。ScanMux が対応するのは Gitleaks 8.30.1 と OSV-Scanner 2.7.0 です。

**破れたら。** 改ざんされた、または不具合のある実行ファイルから固定値を取っていた場合、ScanMux はその実行ファイルをそのまま動かします。検出を見落としたスキャナーは問題のないエンジン結果を返し、その結果は `PASS` の条件に数えられます。

**守り方。** 利用者が設定ファイルで、各ツールを絶対パス・SHA-256・版で固定します。
パスは検査対象のリポジトリの外でなければなりません。
ScanMux は起動のたびにファイルを読んで SHA-256 を固定値と比べ（合わなければ `tool_digest_mismatch`）、ツールの版表示に固定した版が含まれることを確かめます。
対応版以外を設定したエンジンは非対応になります。

Windows のプロセス所有者を通じて起動するツールは、所有者が書き込み共有を許さずに開いたままの実行イメージをハッシュするので、ハッシュしたバイト列がそのまま起動します。
ランタイムポリシー v2 では、ツールを受け入れる前に、記録済みの来歴か配布元の証明を追加で求められます。

**検査。** SHA-256 が固定値と合わないとき、ツールのプロセスが起動しないことを試験で確かめています（`test/assumptions.test.ts`、`test/core.test.ts`、`test/process-tree.test.ts`）。ハッシュの一致が示すのは、読んだバイト列が固定値どおりだったことだけです。固定した配布物が正直で正しいことは示しません。この検査は証明ではありません。

### 任意の Trivy の配布物と内蔵検査規則

**前提。** `tools.trivy` を設定するとき、利用者は取得した Trivy 0.76.1 の配布物と、内蔵の設定不備検査規則、その網羅範囲と鮮度を信頼します。実行ファイルの固定したダイジェストが特定するのはバイト列で、配布元ではありません。侵害された配布物や規則は、問題を見落としたり、プロセスに与えられた権限を悪用しようとしたりできます。

**破れたら。** 誤った、または古い内蔵規則では、計画した入力すべてに結果があっても、設定不備の候補を見落としたり誤検出したりします。侵害された実行ファイルは、ほかの読めるファイルの読取り、書けるファイルの変更、通信を試みられます。AppContainer は厳密なファイルシステムの許可リストを成立させず、すべての通信の遮断も証明しません。後述の未確認点が残ります。

**守り方。** 任意の固定対象は Trivy 0.76.1 で、実行ファイルの SHA-256 は `94618922c9eb324d7099bf217b01504bfc1f87a0d46d6008cb24ec89b1d1a4bb` です。
利用者が検査の外で取得・確認し、ScanMux は検査中に Trivy の取得や規則の更新をしません。
版確認の引数は `--version` だけです。

設定の検査では固定引数を使い、明示した空の設定・ignore ファイル、非公開のキャッシュを指定し、規則更新・版確認・テレメトリーを無効にし、完了証拠として非検出の規則も含めます。
Windows の制限経路は、昇格せず、能力を付与しない AppContainer プロファイルを既存所有者の Job 内で使い、スナップショットと非公開の実行ファイル複製に読取り・実行、非公開の作業領域に変更権限を与えます。
通常プロセスへの代替起動はありません。

所有者がない、プロファイルが使えない、Windows 以外の場合は Trivy を未起動・非対応とし、優先する判定がなければ `INCOMPLETE` です。
ランタイムポリシーの部品名は `trivy` です。
固定した対象範囲と取得時の責任は [Trivy](trivy.ja.md) を参照してください。

**検査。** 固定版の試作実行では、Dockerfile・Kubernetes・Terraform・CloudFormation・Helm でそれぞれ 2・17・8・8・17 件、計52件の不合格の規則を観測しました。
不正な Kubernetes 入力は Trivy が黙って省いたため、終了コード 0 や空でない結果だけでは網羅性を示せません。

計画のファイル・モジュール・チャートの一覧を結果の対象と照合し、欠けた各単位は部分的な範囲として `INCOMPLETE` のままにし、ほかの単位の成功によって解析済みにしません。
試作での通信・ファイルシステムの観測は後述します。
限られた計測であり、隔離や規則の正しさの証明ではありません。

### OSV のオフラインデータベースと受領記録

**前提。** `osvDatabase` が指す OSV データベースの複製は、取得した時点で OSV が各エコシステム向けに公開していたデータで、OSV-Scanner はロックファイルをそれと正しく照合します。

**破れたら。** 改変された、欠けた、または古いデータベースでは、依存関係の検出を見落としたり誤ったりします。それでも結果は、ほかの入力が許すどの判定にも届きます。`PASS` も含みます。

**守り方。** データベースは検査対象のリポジトリの外に置く必要があります。
ScanMux は各 `all.zip` を非公開の作業領域に複製してハッシュします。
`database-receipt.json`（`scanmux.osv-database/v1`）があれば、大きさと SHA-256 がそれと一致しなければなりません。
取得開始の印があって受領記録がない場合は拒否します。

検査の後にもう一度複製をハッシュします（`database_changed_during_scan`）。
レポートには各データベースの SHA-256、ファイル時刻、来歴を残します。
来歴は受領記録があれば `recorded`、なければ `unknown` です。
ScanMux は古いデータベースを拒否しません。
古さは読み手のために記録します。

**検査。** 受領記録の根拠は `locally_recorded_https_acquisition_not_authenticated` です。データベースを取得した機械の上で書かれ、HTTPS で届いたものを記録しますが、署名はありません。受領記録との一致が示すのは、記録を書いた後にデータベースが変わっていないことです。この検査は、データが OSV の公開したものであることの証明ではありません。

### OS、Node 実行環境、Windows のプロセス所有者

**前提。** OS は利用者の分離、ファイルの権限、プロセスの制御を説明どおりに守ります。ScanMux を動かす Node.js（24.16 以上 25 未満）は正規のものです。Windows では、[Windows のプロセス終了](windows-process-termination.md)（英語のみ）に書いたとおり、Job Object がツールのプロセスツリーをすべて止めます。

**破れたら。** カーネル、Node.js、管理者アカウントが乗っ取られていれば、ScanMux 自体がその支配下にあるので、その機械で出た結果には意味がありません。停止後も生き残ったプロセスは、ScanMux が報告した後にスナップショットや出力を変えられます。

**守り方。** Windows では、Git と、エンジンが動かすスキャナーは、固定したプロセス所有者（`tools.windows-process-owner`）を通じて、それぞれ専用の Job Object の中で起動します。
Job は閉じると中のプロセスを終了させ、抜け出しを許しません。
設定したツールを起動するコマンドは、この固定がなければ実行を拒否します。

停止はツリー全体の終了を確かめたときだけ完了と数え、確かめられなければ `termination_unverified` を記録して結果を `ERROR` にします。
ただし、[Windows のプロセス終了](windows-process-termination.md)（英語のみ）に挙げたとおり、すべてのプロセスが所有者を通るわけではありません。

ランタイムポリシーが実行を受け入れる前に動く gh の配布元確認と、ホストジョブ所有者の `--version` の確認は直接起動し、この経路の停止は常に `termination_unverified` として報告します。
ツールを設定していない `doctor`、Gitleaks を設定していない `runner-check`、`engine-history`、`job-scan`、`host-job-scan` は所有者を必要としません。

ScanMux は補助のプロセスもいくつか直接起動し、これらはどの Job にも入りません。
ACL 設定の PowerShell、`runner-check` の後始末の `taskkill`、`runner-check` の Codex CLI、`job-scan`、`host-job-scan`、`runner-check`、`ai-scan` の経路の Docker CLI、所有者のプロセス自身です。

この一覧は起動箇所を読んで挙げたもので、網羅しているとは主張しません。
これらのプロセスの停止確認は Job による保証ではなく、Docker デーモンが起動するプロセスもどの Job にも入りません。
非公開の作業ディレクトリは現在の利用者だけに制限します。
計画には制約 `same_user_concurrent_mutation_not_supported` が付きます。

**検査。** プロセスツリーの試験は Windows で実際のツリーを止め、確認に失敗したときに `termination_unverified` になることを求めます。通常の `scan` は Node.js の実行ファイルをハッシュせず、レポートには版だけを残します。これらの検査は、試した場合を観測したものです。OS についての証明ではありません。

### Git とリポジトリのオブジェクト

**前提。** 固定した Git は対象のコミット済みの内容をそのまま返し、HEAD のコミットは利用者が検査したいものです。

**破れたら。** オブジェクトストアが壊れているか、Git が別の内容を返すと、どのエンジンもそのコミットとは違うものを検査します。

**守り方。** Git はスキャナーと同じく固定するツールです。
システムとグローバルの設定を無効にし、フックを非公開のディレクトリへ向け、`core.fsmonitor` を切り、`protocol.allow=never` で動かします。
対象の `.git/config` と `.git/config.worktree` には同じ許可方針を適用し、未指定のキーは拒否します。セクション名と変数名の大文字・小文字は区別しません。

- 従来のキー：`core.repositoryformatversion`（`0`のみ）、`core.bare`（`false`のみ）、`core.filemode`、`core.logallrefupdates`、`core.symlinks`、`core.ignorecase`、`remote.<name>.url`、`remote.<name>.fetch`、`branch.<name>.remote`、`branch.<name>.merge`、`extensions.worktreeconfig`（`true|false`のみ）。
- 検査中に参照しない情報：`user.name`、`user.email`、`user.signingkey`、`user.useconfigonly`、`push.default`、`push.followtags`、`push.autosetupremote`、`lfs.<url>.access`、`remote.<name>.pushurl`、`url.<base>.pushinsteadof`、`branch.<name>.description`、`.rebase`、`.pushremote`、`.vscode-merge-base`。検査では、これらを読むコミット・署名・push・git-lfs・rebase・エディターの操作を行いません。
- 強制上書きする設定：`core.hookspath`、`core.fsmonitor`、`core.attributesfile`、`core.excludesfile`。対象へのすべてのGit呼出しで非公開の場所または無効な値へ上書きするため、設定されたフック・監視コマンド・外部ファイルは使いません。
- 値を検証する改行設定：`core.autocrlf=false|true|input`、`core.safecrlf=false|true|warn`、`core.eol=lf|crlf|native`。`status`では有効なままにするため、CRLFの作業ファイルがLFのコミット済みblobと異なっても、Gitでは変更なしと判定する場合があります。スナップショットには常にコミット済みblobを使います。

許可するのは列挙した正確なキーだけで、セクション全体は許可しません。include・alias・filterドライバー・SSHコマンド・未対応の拡張・その他のキーは検査前に拒否します。構文は1行の`variable = value`と引用符付きのサブセクションに限定し、不正な行や継続行は拒否します。
拒否時は`plan.blockers`と依存関係の`missing[].code`に`unsupported_git_config:<section>.<variable>`を記録します。名前は正規化したセクション名・変数名（各64文字以内）だけで、サブセクション名や値は含めません。識別子が不正または長すぎる場合は従来の`unsupported_git_config`です。コードを比較する側は、接尾辞付きの形式にも対応する必要があります。
作業ツリーに未コミットの変更があると計画を止めます。

計画には各ファイルのオブジェクト ID、大きさ、SHA-256 を記録し、エンジンを1つ動かすたびにスナップショットをそれと比べます（`snapshot_changed` なら結果は `ERROR`）。
計画には制約 `tracked_files_only` と `git_history_not_scanned` が付き、手元のリポジトリから作った計画には `clean_committed_git_only` も付きます。

**検査。** スナップショットのハッシュは、計画を作ったのと同じ Git から得たものです。実行中の変化は見つけますが、計画時に Git が誤った答えを返したことは見つけません。この検査は証明ではありません。

### 任意の AI エンジン

**前提。** 利用者が `ai-scan` を実行するとき、提供元と Linux のワーカーは、受け入れたコミットの射影だけを処理し、返ってきた候補は人が確認します。

**破れたら。** ソースは、保持と学習の方針を ScanMux が `unverified` と記録している提供元へ送られます。問題を見落としたモデルも、確認を完了したことになります。

**守り方。** AI エンジン（`codex-security`）はすべての計画で必須です。
通常の `scan` はこれを動かしません。
エンジンは `isolation_unverified` を報告するので、結果は良くても `INCOMPLETE` です。
`ai-scan` では、利用者が受け入れた計画ハッシュと完全に一致するときだけ、その計画に記録した上限の中でエンジンが動きます。
Daybreak Blue は任意の上位設定として要求します。

実効値が `standard` または `daybreak_blue` なら AI のプログラム条件を満たし、不明・欠落・要求していないプログラムは未確認のままです。
合成応答、証拠不足、使用量不明、終了未確認は引き続き完了を妨げます。
その検出は常に `code` 区分の候補です。
High/Critical か深刻度不明の候補は判定に確認の理由を加えますが、`FAIL` にはしません。
ただし、いまの最終結果は変わりません。

`ai-scan` も全範囲を解析し終えることのない `runtime-advisories` を必須にしていて、`INCOMPLETE` は `REVIEW` より優先されるので、結果は `INCOMPLETE` です。
それでも助言だけのエンジンではありません。
AI の実行が失敗すれば `ERROR`、終わらなければ `INCOMPLETE` のままで、全範囲を解析して完了することは `PASS` の条件の1つです。

その `PASS` には、現時点ではどのコマンドも届きません。

**検査。** レポートには、要求した access program と実効値を別々に記録し、試行、使用量、送信先、ワーカーの境界を確かめたかどうかを残します。提供元はソフトウェアの証明を出さないので、送信先の記録は `unattestable` です。これらの記録は、提供元が何をしたかの証明ではありません。

### 公開フィードとの照合（KEV と JVN）

**前提。** 固定した URL から HTTPS で取得した CISA KEV カタログと JVN の更新 RSS は、CISA と JVN が公開したものです。鮮度を判断するとき、手元の時計は正しいものとします。

**破れたら。** CVE に付く `listed`、`not_listed`、`observed`、`not_observed_in_window` が誤るか、新しくない複製が `fresh` と表示されます。

**守り方。** `intel-refresh` は固定した各 URL へ GET を1回ずつ送り、リダイレクトを拒否し、本文の大きさを制限して、厳密に解析します。
取得の記録は非公開の保存場所へ追記し、読むたびに大きさとハッシュを確かめ直します。
`intel-match` は結果を別のファイル群に書き、判定・レポート・検査の終了コードを変えません（[公開フィードとの照合](threat-intel.md)、英語のみ）。

**検査。** 解析と保存場所の試験は、ネットワーク取得の関数を差し替えて動かします。どちらのフィードにも署名がないので、署名の確認はしていません。これらの検査は、フィードが正しいことの証明ではありません。

### 利用者の設定ファイルとランタイムポリシー

**前提。** 設定ファイルとランタイムポリシーは利用者が書き、利用者の意図を表し、検査対象のリポジトリを含めてほかの誰も変更できません。

**破れたら。** 誤ったファイルへの固定、受け入れすぎるランタイムポリシー、小さすぎる上限は、何が動くかを変えます。上限が小さすぎると `INCOMPLETE` か `ERROR` になり、誤った `PASS` にはなりません。時間の上限はどちらにもなり得ます。たとえば版の確認が時間切れになるとエンジンの失敗として扱われ、`ERROR` になります。誤った固定は最初の項目の場合にあたります。

**守り方。** 設定ファイルのパスは絶対パスで（違えば `config_must_be_absolute`）、対象の外にあり（`path_inside_target`）、64 KiB 以下でなければならず（`file_limit`）、中身は既知のキーだけにできます（`invalid_config`）。
ツールの名前が未知か、固定値のオブジェクトのキーや値が誤っていれば `invalid_tool` です。

ほかの誤った形も拒否しますが、コードは異なります（ツールの値がオブジェクトでなければ `invalid_report`）。
計画には設定ファイルのダイジェストである `policyHash` を記録し、`scan` は設定ファイルが変わった計画を拒否します（`plan_integrity`、結果は `ERROR`）。
状態が `stopped` のランタイムポリシーは何も起動させず、拒否規則は部品を名前かダイジェストで拒否します。

ランタイムポリシー v2 は検証器と台帳も固定し、どちらも対象の外に置きます。
これらのファイルを利用者だけが書き込める状態に保つのは、利用者の役割です。

**検査。** 設定ファイルの解析と計画への結び付けには試験があります。設定の選び方が正しいかどうかは、ScanMux には分かりません。この検査は証明ではありません。

## ScanMux が保証すること、しないこと

前提とは、結果がよりどころにしているものです。前提が偽なら、ScanMux が気づかないまま結果が誤ることがあります。保証の範囲外はこれとは別で、前提が成り立つかどうかにかかわらず、ScanMux が何も主張しないものです。右の列は保証の範囲外を挙げています。

| ScanMux が保証すること | ScanMux が保証しないこと |
|---|---|
| `PASS` は、必須エンジンがすべて完了して全範囲を解析し、止められた・除外されたものがなく、失敗したエンジンも完全性の誤りもなく、秘密情報・High/Critical・深刻度不明の検出が1つもないときだけ出ます。現時点では、どのコマンドもこの `PASS` に届きません（「結果の意味」を参照）。 | `PASS` はリポジトリが安全だという主張ではありません。固定したツールと規則から見た、1つのコミットの追跡ファイルについての結果です。 |
| 必須の検査が欠けた・失敗した・中断した・時間を超えた・部分的だった場合、`PASS` にはなりません。 | 固定した Gitleaks 8.30.1 の既定の規則に合わない秘密情報は見つけません。Gitleaks の既定の許可リストにあるパスは、検査せずに除外として記録します。 |
| ScanMux が固定して検証するツールは、起動する前にファイルをハッシュして固定した SHA-256 と比べ、合わないものは起動しません。AI/Linux ワーカーの経路の Docker CLI は固定のパスからハッシュせずに起動するので、この保証の対象外です（計画には身元が不明と記録します）。Windows のプロセス所有者を通じて起動する場合は、ハッシュした実行イメージがそのまま起動します。Windows 以外と直接起動する経路では、ハッシュしてから起動するまでの間に差し替えられたファイルを見つけません（「確かめていない点」を参照）。 | 固定したツールが正直で正しいことは示しません。固定が決めるのは、起動してよいバイト列だけです。 |
| 検査の開始時に、計画か読み込んだ設定が記録したハッシュと合わなければ `ERROR`（`plan_integrity`）で終わります。実行中は、エンジンを1つ動かすたびにスナップショットの複製を計画と比べ、変わっていれば `ERROR`（`snapshot_changed`）で終わります。実行中に設定ファイルを読み直すことはしません。 | Git の履歴、ほかのブランチ、追跡外のファイル、追跡されていない、または後から生成されたビルドの成果物、稼働中の環境は検査しません。追跡されているビルドの成果物は追跡ファイルなので検査します。 |
| 停止を確認できない場合は `ERROR` で、成功にはなりません。 | OSV エンジンが依存関係の脆弱性として報告するのは、手元の OSV の複製にあり、OSV-Scanner が読むファイルにあるものだけです。データベースの古さに上限は設けていません。`runtime-advisories` エンジンは、OSV を使わずに、宣言された実行環境の版を組み込みのカタログと照合します。 |
| フィードとの照合は別に書き出し、判定・レポート・検査の終了コードを変えません。 | KEV に載っていることは、その脆弱性が対象で悪用できることの証明ではありません。`not_listed` は、悪用されていないことの証明ではありません。 |
| | AI の候補は確定した検出ではありません。候補のないまま AI の確認が完了しても、問題がないことは示しません。 |
| 任意の Trivy は既存の必須4エンジンを補い、有効にしてもそれらを外したり完了させたりしません。計画した入力単位に応答がなければ部分的な範囲として `INCOMPLETE` のままです。 | Trivy の対象は固定した内蔵規則による5種類の IaC 形式だけです。配置可能性、稼働時の安全、形式への完全対応、規則の鮮度、設定不備がないことは示しません。検出は候補です。 |

## 依存プロジェクトの解析

uv workspaceは、各commitから収集済みの依存入力だけで判定します。`uv.lock`のeditable・virtualがメンバーのパスの正本です。安全な相対パス、収集済みのメンバーmanifest、正規化したプロジェクト名の一致、`[manifest] members`の集合の一致が必要です。`[manifest]`の省略はルートのみを意味します。workspaceの`members`・`exclude`はリテラルのパスか末尾の単一`/*`に限り、条件で選ばれる収集済みmanifestはすべてlock内に必要です。メンバー内のworkspace宣言も扱いません。所属がこの範囲に収まらなければ`workspaces_outside_subset`で`undetermined`のままです。メンバーのmanifest不正や動的依存は、そのメンバーの理由でプロジェクト全体を判定不能にします。

workspace宣言のある仮想ルートは`[project]`を省略でき、依存グループと解決設定だけを提供します。それ以外で`[project]`がなければ`manifest_invalid`です。メンバーの要求は節名に相対パスを付けて統合し、解決設定はルートのみ、sourcesは全メンバーから取得します。manifestのハッシュは全メンバーのmanifestを含みます。追加のファイル読み取りは行わず、既存の入力容量制限と除外条件を適用します。baseとheadは独立に判定します。npm workspaceの`workspaces_outside_subset`とアドバイザリ照合は変わりません。解析が完了しても、更新先を解決・インストールできる証明にはなりません。

## 確かめていない点

- Trivy の Windows 制限実行の試作では、DNS の名前解決の失敗（11001）と直接の TCP 接続の拒否（10013）を観測しました。UDP の `SendTo` 呼出しは成功しましたが、配送は観測していません。UDP の拒否と、すべての通信を遮断するという主張は未証明です。
- Trivy の AppContainer の試作では、All Application Packages に読取りが許された、意図した入力集合の外の兄弟ファイルを読めました。Windows はプロファイルの保存領域も作成します。スナップショットと実行ファイルへの読取り・実行、作業領域の中身への変更権限を与えても、厳密なパスの許可リストや、作業領域だけが書込み可能だとは証明しません。計測した場合を超える、ライブリポジトリと資格情報の隔離は未確認です。
- Trivy の試作の52件の観測が示すのは、試した入力だけです。5形式、外部参照、Terraform モジュール、Helm チャートの完全性は示しません。不正な Kubernetes 入力の黙った省略は、部分的な範囲を維持する既知の理由です。検査では内蔵規則を更新せず、ScanMux は規則の鮮度や配布元を独立に認証しません。
- `intel-refresh` が行う DNS の問い合わせは計測していません。フィードの試験はネットワーク取得の関数を差し替えるので、実際の通信を観測した試験はありません。要求にリポジトリのデータは載りませんが、問い合わせからはフィードのホスト名と更新の時刻が分かります。
- フィードの保存場所の権限検査のうち POSIX 向けの分岐（所有者とモード 0700）は、このプロジェクトの CI で POSIX の機械上では一度も動いていません。2つのワークフローはどちらも `windows-2025` で動きます。
- AI/Linux ワーカーの経路の Docker CLI は固定のパスからハッシュせずに起動するので、SHA-256 の保証は及びません。ScanMux が直接起動する補助のプロセス（PowerShell、`taskkill`、`runner-check` の Codex CLI、Docker CLI、所有者のプロセス）はどの Job にも入らず、その停止確認は Job による保証ではありません。
- Windows 以外と、Windows でツールを直接起動する経路では、SHA-256 の確認とツールの起動が別の手順です。ScanMux はファイルをハッシュしてからパスで起動するので、その間に差し替えられたファイルは見つけません。Windows のプロセス所有者を通じて起動するツールでは、所有者が起動する実行イメージそのものをハッシュします。
- Windows では、プロセス所有者の非公開の複製を、書き込んでから起動するまでの間に、同じ利用者の別のプロセスか管理者が書き換えられます。SHA-256 の確認はこの間を覆いません。
- OSV データベースの受領記録は、上に書いたとおり認証されていません。
- JVN の更新 RSS の利用条件は確かめていません。
